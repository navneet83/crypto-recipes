# Contributing

## What a contribution looks like

- A new language for an existing recipe: one file under `impl/<language>/`, a harness that replays `cases.json` and `negative.json` and supports `--emit N FILE` and `--consume FILE` the same way the existing harnesses do, and a line in the CI workflow. The README table gets a ✅.
- A new recipe: a section in `RECIPES.md`, vectors generated by one implementation and reproduced by at least two others before merge, and negative vectors.
- A fix to an implementation: the vectors do not change. If they would have to, that is a new recipe identifier, not a fix.

## The one rule

No cryptographic primitive is implemented here. No cipher, hash, MAC, KDF, KEM, signature, field arithmetic or constant-time comparison. An implementation calls the platform's standard library, or one of the libraries in the table below. Adding a library to the table is a pull request on its own, with a link to the library's audit or its position in the platform's own guidance.

| Language | Allowed |
|---|---|
| Swift | CryptoKit, CommonCrypto, Security.framework; swift-crypto on Linux |
| TypeScript | WebCrypto (`globalThis.crypto.subtle`); `node:crypto` for what WebCrypto lacks |
| Python | `hashlib`, `hmac`, `secrets`; pyca/cryptography; argon2-cffi |
| Kotlin/Java | JCA (`javax.crypto`, `java.security`); Bouncy Castle for what the JDK lacks |
| C# | `System.Security.Cryptography` |
| Go | standard library `crypto/*`, `golang.org/x/crypto`, `filippo.io/*` |

Where a platform has no implementation of a recipe's primitive, that language ships the fallback profile or marks the recipe as unavailable. It never ships a hand-written primitive.

## Style

Implementations are meant to be read and copied, so they are short, one file, and commented at the top with the key, cipher and layout. Constants are named after the recipe page. Failures throw; nothing returns partial plaintext, nothing logs plaintext or keys.
